## Top 5 blockers (must be resolved before GAP-01 can be attempted safely)

1. **No version control (GAP-18).** Any schema migration attempted without git history is unrecoverable if it goes wrong.
2. **No persisted Manager/Non-Manager attribute (GAP-02).** GAP-01's formula cannot run correctly in production without knowing this per employee.
3. **No Room schema export configured (GAP-17).** Migrations for GAP-01/02 would be written and verified blind without this.
4. **No test coverage for the payroll formula (GAP-10).** A GAP-01 rewrite has nothing to prove it didn't regress `PayrollCalculator`'s already-correct logic.
5. **Unresolved product decision on which formula is canonical (GAP-01 itself, as an open question before it's an engineering task).** Starting the rewrite before the user confirms the direction risks wasted work or the wrong migration shape.

## Top 5 risks if shipped/used as-is today

1. Any payroll a user approves and finalizes right now does **not** reflect Manager/Non-Manager, GP/TJ proration, UM/PH, tiered UL, or PL — it will be numerically wrong relative to the company's actual stated pay policy (GAP-01/02/03/04).
2. A user could mistake the detailed calculator ("Kalkulator Detail per Karyawan") for the real payroll process, since its on-screen disclaimer is the only signal that it changes nothing persisted (`UI_UX_FLOW_AUDIT.md` §4).
3. Real penalties (disciplinary actions) and any cash advances have zero effect on payroll, so a company relying on this app for those deductions will under-deduct silently (GAP-05).
4. Once a nonzero BPJS/tax rate is configured, the truncation-vs-HALF_UP rounding mismatch (GAP-08) will produce a slightly-off statutory deduction every single payroll run.
5. A future entity/column change made without schema export or version control (GAP-17/18) has no safety net — a bad migration could corrupt or lose real company payroll/employee data with no way to diff what changed or roll back.

## Work that should NOT start before its dependencies are resolved

- Do not attempt GAP-01 (formula reconciliation) before: GAP-18 (git), GAP-17 (schema export), GAP-10 (tests), and an explicit user decision on GAP-02 (how Manager/Non-Manager gets persisted) and GAP-01 itself (which formula becomes canonical).
- Do not attempt GAP-05/GAP-06 (deductions/earnings persistence) before GAP-01 is decided, since whatever formula becomes canonical determines where these line items plug in.
- Do not add a Kasbon entity speculatively — wait for the user's explicit confirmation it's in scope (it is currently only mentioned as an example in the original rules prompt, not confirmed as a hard requirement).

## Suggested implementation order

1. GAP-18 (git init) → GAP-17 (schema export) — pure safety/tooling, zero product-behavior risk, do these first and immediately.
2. GAP-10 (write unit tests against the *existing, already-correct* `PayrollCalculator`) — locks in today's correct behavior as a regression baseline before anything else changes.
3. Get the user's decision on GAP-01/GAP-02 (which formula is canonical; how Manager/Non-Manager is persisted) — a conversation/decision, not code.
4. Implement GAP-02 (persisted Manager/Non-Manager) as its own migration, tested in isolation.
5. Implement GAP-01/03/04/07/09 together as one coherent rewrite of the persisted payroll pipeline (they share one root cause and one migration).
6. Implement GAP-05/06 (deductions/earnings persistence) once GAP-01's shape is settled.
7. GAP-08 (rounding fix) rides along with GAP-01's rewrite.
8. P2/P3 items (GAP-11 through GAP-16) can be scheduled independently, in any order, since none of them block or are blocked by the payroll-core work above.

## Measurable acceptance criteria for "GAP-01 is done"

- `PayrollResultEntity` (or its replacement) stores GP/TJ/UM/PH/UL/PL as distinguishable amounts (not folded into one flat `totalAllowance`/`totalOvertimeAmount`).
- For a Manager test employee, approving a period pays GP/TJ/UM/PH in full regardless of attendanceDays.
- For a Non-Manager test employee with attendanceDays < scheduledWorkDays, GP/TJ are prorated (HALF_UP) and UM/PH use the daily rate × attendanceDays.
- A recorded overtime event of exactly 2h produces UL at 100%+150% tiers and PL = 0; an event of 3h produces the 100/150/200% tiers correctly and PL = the configured per-event amount, exactly once.
- Re-running approve on the same period updates existing rows (no duplicates), and finalizing locks the period against further changes — this behavior already exists today and must not regress.
- At least one automated test exists per rule in `BUSINESS_RULES_AUDIT.md`'s summary table, passing against the new, canonical formula.
